Document processing systems are often built around a simple idea: take a large collection of files, split them into smaller pieces, and make those pieces searchable. The details, however, decide whether the system is actually useful.

The first problem is extraction. Office documents, PDF files and plain text all store their content differently. A PDF may contain text as positioned glyphs rather than sentences, so paragraphs have to be reconstructed from line breaks and spacing. A word processing file keeps paragraphs explicitly, but tables, footnotes and headers are stored in separate parts of the archive. Plain text looks easy until you meet a file saved in a legacy encoding, or one that mixes Windows and Unix line endings.

The second problem is segmentation. A language model that turns text into vectors can only read a limited number of tokens at once. If a fragment is too long, the end of it is silently cut off, and whatever was written there will never be found by a search. If fragments are too short, each of them carries too little context: a sentence like "the deadline is ten working days" means nothing without the paragraph that says which process it belongs to.

A common compromise is recursive splitting. The text is first divided into paragraphs. Paragraphs that fit into the limit are grouped together until the next one would overflow the fragment. A paragraph that does not fit on its own is divided into sentences, and a sentence that is still too long is divided into words. Only when a single unbroken string exceeds the limit does the algorithm cut it at an arbitrary position.

Overlap between neighbouring fragments adds a little redundancy. The last few dozen tokens of one fragment are repeated at the start of the next, so a statement that happens to fall on the boundary still appears in full in at least one of them. The cost is a slightly larger index and some duplicate results, which can be removed later when the answers are ranked.

Finally, every number in this pipeline should be measured rather than guessed. The size of a fragment is counted with the same tokenizer that the embedding model uses, the prefix that the model expects is included in the budget, and the special tokens that mark the beginning and the end of a sequence are accounted for. A test that compares these counts with the reference implementation is cheap to write and saves hours of debugging when search quality turns out to be worse than expected.
